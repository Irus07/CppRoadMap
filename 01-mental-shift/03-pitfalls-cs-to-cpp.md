# 03. Топ-10 подводных камней при переходе с C# и C на C++

> Этот список спасёт вам десятки часов дебага. Здесь собраны грабли, на которые наступает почти каждый программист с опытом в C# или C.

---

### 1. Неинициализированные переменные содержат мусор
* **В C#:** Любое поле или локальная переменная гарантированно инициализируется нулём (`0`, `false`, `null`), либо компилятор запрещает чтение (`CS0165`).
* **В C++:** Локальная переменная на стеке без явной инициализации содержит **случайный мусор из стека**.
```cpp
int x; // ОШИБКА: в x лежит произвольный мусор!
int y = 0; // ОК
int z{};   // ОК (Value-initialization / Zero-initialization, z == 0)
```
> **Совет:** Всегда используйте списочную инициализацию: `int count{};` или `int count = 0;`.

---

### 2. Привычка писать `new` на каждый объект (C# habit)
* **В C#:** `var user = new User();`
* **В C++:** Написание `User* user = new User();` выделяет память в куче и **никогда её не освободит**, пока вы вручную не напишете `delete user;`. Если выбросится исключение до `delete`, память утечёт навсегда.
```cpp
// ПЛОХО (в стиле C#):
User* u = new User(); 

// ХОРОШО (Modern C++ стек):
User u; 

// ХОРОШО (если куча действительно нужна):
auto u = std::make_unique<User>();
```

### 3. Иллюзия разницы между `struct` и `class`
* **В C#:** `struct` — структура данных на стеке, копируемая по значению. `class` — объект в куче по ссылке.
* **В C++:** В C++ `struct` и `class` **на 100% идентичны по поведению и производительности**. Единственное отличие — видимость по умолчанию:
  * В `struct` поля и методы по умолчанию `public`.
  * В `class` поля и методы по умолчанию `private`.
> **Конвенция в C++:** используйте `struct` для простых DTO/POD (Plain Old Data) без сложного инварианта, а `class` — для инкапсулированных типов с приватными полями.

### 4. Срезка объектов (Object Slicing)
В C# полиморфизм работает всегда. В C++ полиморфизм работает **только по ссылке (`&`) или указателю (`*`)**.

```cpp
class Base { public: virtual void Print() { std::cout << "Base\n"; } };
class Derived : public Base { public: void Print() override { std::cout << "Derived\n"; } };

void Show(Base b) { // ПЕРЕДАЧА ПО ЗНАЧЕНИЮ!
    b.Print();
}

Derived d;
Show(d); // Выведет "Base", а не "Derived"!
```
**Почему это произошло?** Параметр `Base b` выделил на стеке память ровно под размер `Base`. Объект `Derived` был обрезан (sliced) до базового класса при копировании!
* **Как правильно:** `void Show(const Base& b)` — полиморфизм сохранится.

### 5. Забытый виртуальный деструктор (Утечка ресурсов при наследовании)
Если у вас есть полиморфный базовый класс, его деструктор **обязан** быть объявлен как `virtual`:

```cpp
class Base {
public:
    virtual ~Base() = default; // ОБЯЗАТЕЛЬНО!
    virtual void DoWork() = 0;
};

class Derived : public Base {
    std::vector<int> data; // Вектор в куче
};

Base* ptr = new Derived();
delete ptr; // Если ~Base() не виртуальный, вызовется только деструктор Base!
            // Деструктор Derived не вызовется, data утечет. Это Undefined Behavior.
```

### 6. Написание кода на «C в C++»
Если вы писали на C, велик соблазн использовать привычные функции:
* `malloc()` и `free()` вместо `new`/`delete` или `std::make_unique`.
* `char str[256]` и `strcpy()` вместо `std::string` или `std::string_view`.
* `printf()` / `scanf()` вместо `std::print` (C++23) или `std::cout`.
* Массивы `int arr[10]` вместо `std::array<int, 10>` или `std::vector<int>`.

> **Почему это опасно?** Функции C (`malloc`, `free`, `memset`) не вызывают конструкторы и деструкторы C++ объектов! Применение `malloc` к классу с полями `std::string` приведёт к моментальному краху программы.

### 7. Сравнение знаковых и беззнаковых чисел (Signed vs Unsigned)
В STL методы `.size()` возвращают беззнаковый тип `size_t` (64-битный `unsigned long long` на x64).

```cpp
std::vector<int> v;
int i = -1;

if (i < v.size()) { 
    // ВЫ ДУМАЕТЕ, ЧТО ЭТО TRUE (-1 < 0)?
    // НЕТ! Это FALSE!
}
```
**Почему?** При сравнении `i` неявно приводится к беззнаковому типу `size_t`. Число `-1` в беззнаковом представлении превращается в `18446744073709551615` (максимальное 64-битное число).
* **Решение:** Включайте предупреждения компилятора (`-Wsign-compare` / `/W4`) и используйте `ssize()` (C++20) или аккуратное приведение типов.

### 8. Неопределённое поведение (Undefined Behavior — UB)
В C# среда выполнения (CLR) бросает безопасные исключения: `NullReferenceException`, `IndexOutOfRangeException`, `DivideByZeroException`.

В C++ **понятие UB означает, что компилятор имеет право делать всё что угодно**:
* Стереть код проверки;
* Выдать мусор;
* Вызвать аварийный сбой сегментации (Segfault / Access Violation);
* Программа может 1000 раз отработать «нормально», а на продакшене уйти в бесконечный цикл.

Примеры UB:
1. Выход за границы массива (`arr[100]`).
2. Разыменование нулевого указателя (`*nullptr`).
3. Знаковое переполнение `int` (`INT_MAX + 1`).
4. Чтение из освобождённой памяти (Use-After-Free).

### 9. Инвалидация итераторов и ссылок
В C# при модификации коллекции во время `foreach` вы получите `InvalidOperationException`.
В C++ при добавлении в `std::vector` может произойти перевыделение памяти в куче (reallocation):

```cpp
std::vector<int> v = { 1, 2, 3 };
const int& first = v[0]; // Ссылка на первый элемент

v.push_back(4); // Если вектору не хватило capacity, он выделил новый буфер и переместил элементы!

std::cout << first; // ОШИБКА: first указывает на старый, уже удаленный буфер памяти! (Dangling reference)
```

### 10. `const` в C++ — глубже, чем `readonly` в C#
В C# `readonly` защищает только саму переменную от перезаписи ссылки (но состояние объекта внутри можно менять).
В C++ `const` обеспечивает **транзитивную константность (Deep Constness)**:
```cpp
class Window {
    int width = 800;
public:
    int GetWidth() const { // Метод const не имеет права менять поля класса!
        // width = 1000; // Ошибка компиляции!
        return width;
    }
};
```
Если метод не изменяет состояние объекта, он **обязан** быть помечен как `const`. Иначе его нельзя будет вызвать у константной ссылки (`const Window& w`).
